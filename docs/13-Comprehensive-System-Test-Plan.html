1. Purpose, Scope and Exclusions

This master plan defines an executable, risk-based verification program for Jima. It covers browser behavior, REST contracts, authorization boundaries, persistence, operational resilience and formal acceptance. The companion workbook is the execution record: testers must enter actual results, evidence links, defects, tester, date and environment there.

1.1 In scope

Environment/build readiness; authentication, sessions and logout; all named roles; restaurant/branch isolation; dashboard; complete POS and order lifecycle; coordinator and kitchen; payments and shifts; menu; tables; staff/branches; branch inventory, procurement and adjustments; legacy Item Requests; Main Store receipts and Branch Stock Requests; notifications; reports/exports; daily summaries; responsive behavior at 320, 390, tablet and desktop; accessibility; browser compatibility; validation/error/loading/empty/retry; API/status codes; database transactions; concurrency/idempotency; OWASP-oriented security; privacy/logging/secrets; performance/load; backup/restore/rollback; deployment and smoke; UAT/sign-off.

1.2 Explicit exclusions

  • Destructive security exploitation, denial-of-service against shared or production systems, social engineering, and access to real customer/staff data.
  • Unapproved production data mutation, production seed execution, and schema synchronization against production.
  • Features not defined by the authoritative baseline, including a password self-service flow, offline operation, native mobile applications, and WebSocket realtime delivery.
  • Third-party payment settlement beyond Jima's recording of cash/card/wallet methods unless a contracted integration is separately documented.

2. QA Principles and Test Basis

  • No fabricated success: planned work is never marked Passed without reproducible evidence.
  • Backend is authoritative: hidden UI controls do not prove authorization; direct API denial is required.
  • Risk and traceability: critical money, stock, tenant and authentication paths execute first and map to requirements.
  • Atomicity: multi-write order, payment, table, purchase and stock operations must commit completely or roll back completely.
  • Isolation: every relevant read and write is checked across both branch and restaurant boundaries.
  • Safe evidence: all screenshots, exports, traces and logs are redacted; no secrets or real credentials enter the workbook.

The FRS/SRS define acceptance targets, while production-readiness status defines known gaps. Documentation approval alone is not implementation or pass evidence.

5. Entry, Exit, Severity and Priority

5.1 Entry criteria

  • Versioned release candidate and change scope supplied; static/build checks available.
  • QA environment reachable with authoritative Next.js → NestJS → PostgreSQL routing and synthetic data.
  • Requirements, known gaps and role/scope matrix reviewed; no unresolved environment blocker.
  • Backup/reset, logging and evidence repository ready; testers have least-privilege accounts.

5.2 Exit criteria

  • 100% of mandatory Critical and High-priority cases executed and passed; agreed regression completed.
  • No unresolved Critical or High defect. Medium/Low residual risk is documented and formally accepted.
  • Role/tenant isolation, payment/table and stock transaction evidence is complete.
  • Security, accessibility, performance, migration, backup/restore, rollback, staging smoke and UAT gates are signed.

5.3 Defect severity

SeverityDefinition
CriticalUnauthorized tenant access; secret/password exposure; unrecoverable data loss; incorrect money/stock commit; complete outage; no safe workaround.
HighCore role workflow unavailable or materially incorrect; authorization bypass; duplicate payment/transfer; major reporting error; rollback failure.
MediumImportant behavior degraded with a safe workaround; limited validation, compatibility, accessibility or export issue.
LowCosmetic, wording or minor usability issue without data, security or workflow impact.

5.4 Priority

Critical: release-blocking path, execute every candidate. High: major business/risk path, execute before broad regression. Medium: normal planned coverage. Low: execute as capacity permits unless required for acceptance.

6. Evidence Rules and Defect Lifecycle

Evidence must identify Test ID, timestamp/timezone, release/environment, actor and scoped IDs. UI evidence includes before/action/after screenshots; API evidence includes method/path, redacted request, status and response; transactional evidence includes before/after balances, linked row IDs and audit actor/time; non-functional evidence includes tool configuration and raw summary. Never attach JWTs, passwords, database URLs, secret values or real PII.

Defect lifecycle: New → Triaged → Assigned → Fixed → Ready for Retest → Closed, with Reopened, Deferred or Rejected only by documented decision. Every defect links a Test ID, release, environment, reproduction steps, expected/actual, severity/priority and redacted evidence. A fix requires focused retest plus risk-based regression.

7. Specialized Quality Approaches

7.1 Security and privacy

Use a non-destructive OWASP-oriented review: authentication/session failure, broken object/function authorization, tenant reference tampering, DTO/mass-assignment, safe injection strings, output encoding, CORS/security headers, Swagger/seed exposure, dependency findings, secrets and log redaction. Verify bcrypt hashes and mandatory JWT secret without extracting values. Do not perform denial-of-service, destructive injection or production exploitation.

7.2 Performance

Measure NFR-01: ordinary pages within 2 seconds on typical broadband and list endpoints within 500 ms at 10,000 orders. Agree user/concurrency volumes before execution. Include warm-up, percentile latency, errors, throughput, database pool/CPU/memory, polling behavior and report/export memory. Stop on instability or data-integrity risk.

7.3 Accessibility and responsive

Apply WCAG 2.1 AA-oriented manual and automated review: keyboard, focus, labels/errors, dialogs, headings/landmarks, non-color cues, contrast, zoom and touch targets. At 320 and 390 px verify stacked POS, intentional category scrolling, independent menu/cart vertical scrolling and reachable final action; repeat representative workflows on tablet and desktop.

7.4 API, transactions and concurrency

Verify method/path, documented JSON and 2xx/400/401/403-or-safe-404/404/409/5xx behavior. Unknown sensitive fields must fail safely. Use controlled simultaneous clients to test duplicate order, status, payment, receipt and transfer operations. Check idempotency and database outcome, not UI messages alone.

7.5 Main Store transfer focus

Request and decision never mutate stock. Destination is derived from the Branch Storekeeper. Only destination Manager or same-restaurant Owner decides; only same-restaurant branchless Main Store Storekeeper fulfills. Fulfillment locks and validates every line before one atomic central decrement, branch increment/create, movement, adjustment, post-balance and actor/time commit. One insufficient line rolls back everything. Legacy Item Requests remain separate.

8. Release Gate, Rollback and Sign-off

8.1 Release gate

  • Mandatory test completion and pass criteria met; no unresolved Critical or High defect.
  • Strong JWT secret, no fallback/startup account mutation, restricted CORS, restricted Swagger/seed, DTO controls and reviewed dependency/static findings.
  • Production synchronize disabled; reviewed migrations, restorable backup and tested rollback recorded.
  • Monitoring, retention, alerting and incident ownership active.
  • Staging smoke, performance/security/accessibility reviews and UAT approved.
Deployment remains blocked if any mandatory gate is Failed, Blocked, Not Run, unsupported by evidence, or approved only verbally. It is also blocked while any Critical or High defect is unresolved.

8.2 Rollback criteria

Immediately invoke the approved rollback when authentication, role/tenant isolation, order/payment/table integrity, Main Store or branch balances, migration health, reports, or core availability fails; when error/latency thresholds are exceeded; or when monitoring detects secret/data exposure. Stop further changes, preserve evidence, notify owners, restore the known-good application/database checkpoint as designed, reconcile post-rollback data, and repeat mandatory smoke. Do not chain unreviewed production hot fixes.

8.3 Sign-off

QA Lead recommends based on evidence; Security, DBA/Release and business owners sign their gates; the authorized release owner makes the final Go/No-Go decision. Blank signature fields or conditional approvals do not equal approval.
